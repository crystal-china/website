# 评论删除与撤回

## 规则

| 评论类型 | 可以删除的条件 | 不满足条件时 |
| --- | --- | --- |
| 根评论 | `descendants_count == 0`，所有层级的后代均已软删除 | 撤回正文 |
| 子评论 | `children_count == 0`，直接回复均已软删除 | 撤回正文 |

以上删除条件适用于普通作者。管理员可以删除任意公开可访问的评论，并将该评论及全部后代一起软删除，包括已撤回的评论。
管理员按钮会提示删除范围包含全部回复；普通用户不能通过请求参数开启级联删除。

撤回卡片仍可见、仍参与计数和分页。普通作者删除子评论时，只删除本条；管理员删除子评论时，还会删除它的全部后代，不影响同一根评论下的其他分支。

管理员级联删除复用 `DeleteComment`，在删除事务中通过递归查询沿 `parent_id` 找到后代。
本次新删除的记录使用相同的 `soft_deleted_at`；之前已删除的记录不改时间。正文、楼层、投票及撤回状态保留，后代记录的编辑时间也不变。
只对直接被管理员操作的评论发送删除通知，不逐条通知后代作者。计数仍由 trigger 维护，批量修改完成后重算主题活动信息。
目前回收站仍逐条恢复，尚未提供按本次删除时间批量恢复；必须先恢复所属主题／文档，再按父子顺序恢复评论。

例如 A → B → C → D：D 删除后，C 的直接回复数变为零，可以删除 C；之后 B 也可以删除。根评论 A 必须等到所有未删除后代都消失后才可删除。

## 撤回和恢复

`withdrawn : Bool` 默认是 `false`。两个 Action 直接通过 `Comment::SaveOperation.update!` 将它设为 `true` 或 `false`，不再单独定义 Operation。

两种操作都保留 `content`、`content_html`、编辑时间、楼层、评论计数及已有投票。普通新建和编辑继续拒绝空白正文；撤回期间先恢复，才能再次编辑或投票。

撤回后整张卡片缩成一条提示，不显示作者、头像、时间、楼层或投票。作者或管理员可以恢复；没有回复时还可以删除。根评论仍向所有读者提供展开回复按钮，不隐藏后代。

撤回和恢复不发送通知，既有通知快照不清除。管理员删除他人评论时仍沿用原有删除通知。

通知仍链接到 `/comments/:id`，通过原来的分页定位流程找到撤回卡片并高亮，不返回 404。只有软删除、根评论或主题被删除、文档不可访问时，才显示内容不可用页面。

## 局部刷新与并发

撤回和恢复只返回 `Comments::CardBody`，替换 `comment-ID-body`。外面的 `article` 和回复列表不在替换范围内，不需要用 `hx-preserve` 保留回复列表。

删除、撤回和恢复都先淡出一秒再替换。根评论主体使用 `display: contents`，动画应用到主体的直接子元素，回复列表不会一起淡出。撤回和恢复不弹确认框；删除确认提示“删除后无法回复”。

展开／折叠按钮与回复列表一起放在独立的 `comment-replies` 区域，始终位于评论操作栏下方同一位置。折叠时显示圆形加号和回复数量，展开后原位置显示圆形减号和折叠文字。分支弯线和图标均使用 CSS，不需要 SVG 或布局 JS。

例如 A 已展开 B、C，撤回 A 时只更新正文和操作按钮，B、C 以及减号按钮完全不参与替换；如果原本折叠，则仍保持折叠。不再需要额外的保留状态参数或 `hx-preserve`。

`Comments::ListMore` 判断当前评论与定位目标的关系：目标根评论收到 `reply_expanded: true` 和目标 ID，目标评论收到自己的 ID，其余评论的目标 ID 为 `nil`。`Card` 不再判断根评论关系，也不再接收完整的目标评论对象。

新增、删除子评论直接返回完整的 `Comments::Replies`，替换 `comment-ID-replies`，一次更新展开按钮和回复列表，不再单独 partial 更新 toggle。根评论正文中的操作区仍通过 `hx-partial` 更新：最后一条回复删除后，展开按钮消失，父评论重新显示删除按钮，即使父评论已经撤回。

普通展开、排序和加载更多仍只更新内部列表 `comment-ID-replies-list`，折叠也只清空这个列表，不替换整个回复区域。

回复、删除、撤回和恢复均在事务内先锁根评论，再锁目标评论。回复在取得锁后重新检查可见性，删除在取得锁后检查最新计数。

## 阅读顺序

1. migration 和 `src/models/comment.cr`：新增状态、保留原有删除条件。
2. `src/actions/htmx/comments/withdraw.cr`、`restore.cr`：权限、事务、切换状态与评论主体响应。
3. `src/components/comments/list_more.cr`、`card.cr`、`replies.cr`：定位关系、回复展开与整个回复区域的渲染。
4. `src/components/comments/card_body.cr`：正常主体和撤回后的紧凑主体。
5. `src/components/comments/card_controls.cr`、`delete_or_withdraw.cr`：恢复、删除、撤回按钮。

## 分页计数与部署

主评论区使用 `comment_threads.root_comments_count`，只统计未软删除的根评论；根评论下的子分页使用已有的 `comments.descendants_count`。撤回不改变数量。trigger 在新增、软删除、恢复和物理删除时维护计数，普通分页不再调用 Avram 自动执行 COUNT 的 `paginate`。

通知定位仍需计算目标评论前面有多少条记录，以确定它所在的页码；这个 COUNT 不是总数统计，继续保留。

部署时先执行 `lucky db.migrate`，再重启服务。`20261025120000_add_root_comments_count_to_comment_threads.cr` 会在同一次迁移中创建计数和 trigger，并自动回填已有记录，不需要另跑回填任务。

如果以后手工修改数据造成计数不一致，可运行 `bin/tasks db.fix.soft_delete_counts`，同时重建根评论数、直接回复数和后代数。这个 task 不改编辑时间、不发通知。
