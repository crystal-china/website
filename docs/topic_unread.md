# 主题未读

## 第一版规则

- 仅登录用户拥有已读状态，保存在独立的 `topic_reads` 表；不修改 `topic_follows`。
- “近七天未读”指最近 7 × 24 小时有活动，而且没有读过当前内容的主题。七天边界包含在内。
- 普通列表的未读蓝点不限制时间；例如十天前的主题从未打开，仍有蓝点，但不进入“近七天未读”列表。
- 从未打开的新主题算未读；旧主题有新回复后也可以重新进入列表，不限定主题创建时间。
- 打开主题即认为当前版本已读，不要求展开评论、加载所有分页或滚动到底。
- 自己发布主题、自己新增回复时，也记录已读位置；不把自己的新回复留成未读。
- 编辑、投票、撤回／取消撤回不产生新回复，不会因此让其他用户重新未读。主题编辑成功后会展示详情页，将操作者标记为已读；评论编辑本身不写阅读位置。
- 主题被软删除后不出现在公开列表，阅读记录保留。恢复回复后，已经读过的回复不会让游标倒退。
- 访客阅读、搜索结果、列表、回收站预览不写阅读记录。
- 打开主题时，同步该主题及本次阅读位置以内的评论通知；其他主题、文档评论和之后新增回复的通知不受影响。
- 点击通知进入主题也走相同流程；“全部通知标为已读”只清理通知，不修改主题阅读位置。
- 七天只是筛选范围，不是阅读记录的保存期限；不自动删除旧阅读记录。

例如，小明昨天读过一个月前发布的主题 A，今天小红回复了 A，A 会重新出现在小明的未读列表中。小明再次打开 A 后，它就从未读列表消失。如果只有作者编辑了标题，则仍然保持已读。

## 数据与流程

`topics.last_reply_id` 缓存可见回复中的最大 ID，不需要列表逐条查询评论。最后回复人和活跃时间也取自这条回复，统一按 ID 选择最后回复。

- 新回复：在原有 `record_topic_reply` trigger 中，与数量、作者、时间一起维护。
- 删除／恢复：在原有 `TopicActivity.refresh` 中一并重算。
- 初始建表直接包含该字段，空库从无回复开始；现有数据可用 `db.fix.topic_activity` 重算。

`topic_reads` 每个用户、每个主题只有一条记录：

| 字段 | 含义 |
| --- | --- |
| `topic_id`、`user_id` | 确定阅读的是哪个主题、哪个用户 |
| `last_read_reply_id` | 阅读高水位；0 表示已经读过尚无回复的主题，不是评论外键 |
| `last_read_at` | 最近记录已读位置的时间，浏览、发帖和回复都可能更新 |
| `created_at`、`updated_at` | 普通记录时间；创建时间保留首次建立阅读记录的时间 |

索引包括 `(topic_id, user_id)` 唯一索引和 `user_id` 索引。删除用户或物理删除主题时，关联阅读记录级联删除。

这张表可以统计建立过阅读记录的用户，但其中也包含发帖、回复时自动记录的作者，不能直接等同于实际打开过详情页的独立读者。与关注表关联可统计这些用户中有多少人关注主题，但不能直接当作“阅读后关注”的转化率；它不包含访客，也不是访问日志，无法还原精确 PV、历史每日访问或完整事件顺序。

`TopicReading.mark_as_read` 使用单条 `INSERT ... ON CONFLICT`，不先 SELECT。用 `GREATEST` 保留更大的阅读位置，避免旧标签页把新位置覆盖掉。例如先读到回复 120，再提交旧页面的 110，最终仍保存 120。

打开可访问的主题时，在同一事务中同步相关通知和读取时拿到的 `topic.last_reply_id`，然后使用更新后的用户计数渲染页面。不会重新查询最新回复并把之后新增的回复一起标记。新增主题／回复的 callback 只记录发送者阅读位置，不清理通知，失败回滚时不会留下已读状态。

例如主题最新回复为 205，本次打开会把该主题通知及 `comment_id <= 205` 的评论通知标为已读。`NotificationQuery.unread_in_topic` 的参数 `last_read_reply_id` 就表示这个截止位置；尚无回复时仍处理主题本身的通知。

点击通知会先把该条通知标为已读，再跳转到目标。目标是可访问的主题或主题评论时，最终进入同一主题展示流程，继续同步阅读位置和相关通知。目标返回 404 时不会完成主题阅读处理，但之前点击的那条通知已经标为已读。

Doc 评论仍有回复、提及和关注用户动态的通知，但不使用 `topic_reads`，直接打开文档也不批量清理其评论通知。已读通知保留为历史记录，不等于删除通知。

## 查询与界面

`TopicQuery.unread_by(user_id)` 用带用户条件的 `NOT EXISTS` 排除已读位置已经覆盖当前回复的记录，不限制主题活动时间。`Forum::Index` 仅在开启“近七天未读”筛选时追加 `last_active_at >= 当前时间 - 7.days` 条件。Avram 现在也支持额外 JOIN ON 条件，但这个存在性判断不需要改写成 JOIN。

普通列表只对本页主题批量查询一次未读标记，而且只取 ID，不重复读取主题正文或缓存 HTML；“仅未读”列表直接复用已筛选出来的主题 ID。不逐条查询评论或阅读记录。

社区列表中，按用户筛选的关注／未读分页需要 `COUNT`；普通分页仍使用现有 Space／Node counter。未读数量随用户、时间和筛选组合变化，没有新增难以维护的未读总数 counter。

标题旁蓝点表示该主题对当前用户仍有未读内容，不受七天范围限制。未读开关可与“仅关注”和节点组合，详情页、节点链接、侧栏和分页保留参数 `only_show_unread`。Canonical URL 不包含这些浏览参数。

首次部署不猜测历史阅读行为；没有阅读记录的已有主题显示未读蓝点，其中最近七天有活动的主题进入“近七天未读”列表，打开后建立个人记录。

社区每页条数直接使用 `App::DEFAULT_PER_PAGE`，当前为 20，定义和使用范围见[公共分页条数](topic_counters.md#公共分页条数)。时间范围由 `TopicReading::UNREAD_PERIOD` 控制，当前为 7 天；只有筛选列表应用它，普通列表蓝点不受限制。

时间筛选和排序复用 Topic 的 `(last_active_at, id)` 索引；指定节点时另有 `(node_id, last_active_at, id)`。个人阅读记录通过 `(topic_id, user_id)` 唯一索引查找，没有新增个人未读总数 counter。

## Review 顺序

1. Topic 和 Comment 建表 migration、`CreateTopicReads`、`TopicRead`、`TopicReadQuery`：先看数据结构和缓存维护。
2. `TopicReading`、`TopicQuery.unread_by`：再看写入和判定。
3. `CreateTopic`、`CreateComment`、`ReplyToComment`、`CommentCreation`、`ForumAction.render_topic`：看什么时候标记已读。
4. `Forum::Index`、`Forum::List`、`Forum::IndexPage`、`ForumLayout`、`Forum::ShowPage`：看筛选、标记和参数传递。
5. `topic_reads_spec.cr`：覆盖迁移、时间边界、账号隔离、新回复、删除恢复、筛选组合和分页。

## 部署

主题最后回复字段和 trigger 已合并进初始建表 migration，`topic_reads` 保留独立建表。新环境在空库执行 `bin/tasks db.migrate`，再运行 `bin/tasks db.seed.required_data`，无需回填。

已有数据库须先使用压缩前的版本执行两条 migration，增加 `last_reply_id` 并创建 `topic_reads`，然后再升级到压缩后的版本。如果只迁移数据库、仍运行旧网站代码，正式升级代码时补跑 `bin/tasks db.fix.topic_activity`，重算期间可能过期的最后回复信息。

### 实现边界

实现会分成三层，便于你之后 review：

- `topic_reads` 单独保存已读位置，不改 `topic_follows` 的含义。
- Topic 缓存最后回复 ID；新增回复沿用现有 trigger，删除／恢复沿用活动信息重算。
- 列表增加“近七天未读”筛选和小圆点，可与节点、仅关注组合。

自己发布主题或回复也会标记已读；编辑、投票和撤回不改变阅读状态。七天按最近活动时间计算，普通访问只记录这次打开时拿到的主题版本。
