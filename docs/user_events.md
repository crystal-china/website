# 用户事件记录

`UserAudit` 现在保存用户事件，入口是用户菜单和个人主页中的“账户记录”（`/me/events`）。本人和管理员可以查看，每页 20 条，最新事件排在最前面。管理员从他人主页进入时，通过 `user_id` 指定目标用户，页面会显示记录属于谁；普通用户请求查看其他人的记录会返回 403。

- `ProfileChanged`：修改昵称、登录用户名、头像、签名或个人介绍，记录字段名和变更前后的值。清空可选资料时，新值可以为空。
- `PasswordChanged`：通过个人设置或找回密码修改密码，只记录事件和时间，不保存密码、确认密码或哈希。
- `OauthSignedIn`：每次成功的第三方登录，记录平台名称和时间，不保存令牌。
- `PasswordSignedIn`：每次成功的密码登录，只记录事件、用户和时间，不保存密码。失败登录、普通页面访问及刷新会话不产生此事件。
- `PasswordRemoved`：管理员移除本站密码，禁用密码登录并使旧会话失效，不删除账号。

`user_id` 是记录所属的用户，`actor_id` 是实际操作者。本人操作时两者相同；管理员修改他人资料或密码时，记录管理员为操作者。操作者账号删除后，事件仍保留，界面显示操作者未知。

个人设置中的“上次修改密码”来自最近一次 `PasswordChanged` 或 `PasswordRemoved` 事件。没有历史记录时显示时间未知，不以注册时间冒充修改时间。

普通用户的登录用户名仅能在注册后的前 7 天修改，不是每隔 7 天修改一次。超过期限后字段只读，服务端也会拒绝修改；昵称、头像、密码不受此限制。管理员不受改名期限限制，但同样必须通过格式、长度和唯一性校验。账户记录使用相对时间（如“5 分钟前”），悬停可查看完整时间。

本人和管理员从用户主页的“编辑个人资料”进入 `/users/:id/edit`，统一通过 `PUT /users/:id` 保存。仅本人或管理员可以访问；操作者由服务端传入，不接受浏览器指定。保存成功后返回该用户主页，仅编辑本人时刷新当前登录会话。管理员可使用“上次修改密码”后的“移除密码”按钮；它是独立提交，不保存表单中其他尚未提交的改动。

签名 `tagline` 和个人介绍 `bio` 保存在 `users.profile` JSONB 中，默认 `{}`，不需要额外回填。签名最多 80 个字符，个人介绍最多 3000 个字符，均以纯文本展示，不解析 Markdown 或发送提及通知。个人主页显示两者，社区作者卡片只显示签名；未填写的字段不显示。修改时按字段记录事件，不把整个 JSON 当成一条记录。

旧的 `@用户名` 链接暂不随改名更新；目标不存在时返回 404。

## 会话失效

`users.session_version` 在密码修改或移除时轮换，与密码在同一条 SQL 中保存。浏览器会话和 API 令牌都必须匹配数据库中的当前版本，因此旧凭据在下一次请求时被拒绝。不会主动关闭已经打开的页面，也不能撤销已经通过身份验证、正在处理的请求。

本人改密、重置密码成功后，当前浏览器换发新会话并继续登录；其他旧会话和 API 令牌失效。管理员修改他人密码不影响管理员自己的登录。昵称、头像等普通修改及失败的保存不轮换版本。

版本轮换集中在 `User::SaveOperation#changes`，覆盖现有所有密码保存入口。不要通过 Query 批量更新或直接 SQL 修改密码，否则会绕过这一逻辑。

首次记录 OAuth 登录时，如果账号已有本站密码，会提醒用户确认该密码是否由本人设置。历史 OAuth 登录没有记录可回填，因此这里判断的是启用事件记录后首次记录的登录。

部署时执行 `bin/tasks db.migrate` 即可，无须额外回填任务。迁移直接删除旧 audit 表，重建为空的用户事件表，旧记录不保留。回滚会重建旧表结构，但不会恢复已删除的数据。

后续的 `20261016120000_add_account_management_to_users.cr` 保留现有事件，为历史事件补上本人作为操作者，找不到用户的记录保持未知。它同时添加会话版本字段，不改现有密码。先执行 migration，再启动新版服务；上线后旧浏览器会话和 API 令牌因没有版本标记，会统一失效一次，需要重新登录获取新凭据。

密码事件分别由 `UpdateUser`、`ResetPassword` 的保存回调写入，与用户修改处于同一事务；OAuth 事件在回调验证并获得用户后写入。今后新增密码修改入口时，也应写入同类事件。
