## 通知功能

  全新环境通过 `bin/tasks db.migrate` 创建完整结构，再运行 `bin/tasks db.seed.required_data`
  创建默认 Space 和社区节点，无须执行用户名或正文 HTML 回填。尚未升级的旧站点须先按[历史升级要求](用户名与提及.md#现有环境升级)使用
  压缩前版本完成升级，再切换当前版本。

  提及解析规则改变后，应停止服务器，使用新版本任务运行：

  ```bash
  bin/tasks db.rebuild.content_html
  ```

  重建包含软删除的主题和评论，只更新正文 HTML，不修改编辑时间，不补发或撤销历史
  通知。完成后再启动服务器。

  ### 使用与通知规则

  登录用户可以点击导航栏铃铛，在弹窗中查看通知，每页二十条。新增回复会通知主题作者
  和被直接回复的用户，排除发送者本人，并避免同一次操作给同一个人重复发送。

  登录后可以在其他人的主题详情页点击“关注”，接收该主题后续的新回复通知，包括子回复。
  默认不关注，发过回复也不会自动关注；主题作者本来就收到回复通知，不显示关注按钮。
  同一次回复按提及、直接回复、主题作者、主题关注的优先级发送，每人只收到一条通知。
  取消关注不删除历史通知，直接回复和提及通知不受影响；再次关注只接收此后的新回复，
  不补发旧回复。编辑、删除、恢复内容不向关注者发送通知；主题软删除后保留关注关系。

  登录后，在其他用户的个人主页点击“关注”，接收其新主题和新评论通知，包括文档评论、
  子评论及更深层回复。不能关注自己，未登录时不显示关注按钮。取消关注仅停止此后的
  用户关注通知，不删除历史通知；再次关注不补发以前的动态。编辑、删除、撤回或恢复
  内容不会产生用户关注通知，也不会通知管理员编辑内容时的原作者关注者。

  个人主页的“关注”列表公开可见，按最近关注排序，每页二十人，切换和翻页只刷新
  列表。登录后可直接关注或取消关注；查看他人的列表时，按钮反映当前访问者的关注状态，
  不修改主页主人的关注关系。取消关注只更新按钮，暂时保留当前行；如果查看的是自己的
  “关注”列表，重新加载后该行才会移除，别人的列表和自己的“关注者”列表不因此移除该行。

  并列的“关注者”列表显示关注该账号的人，同样公开、按最近关注排序并支持分页。
  关注者列表复用相同的用户行和按钮；回关与取消关注只改变当前访问者的关注关系。

  同一次操作对每个收件人最多发送一条通知，优先级从高到低为：明确提及、直接回复、
  主题作者、主题关注、用户关注。例如小明既关注作者又关注主题，作者回复时只发主题
  关注通知；如果还明确 @小明，则只发提及通知。关闭 @提及通知不会关闭关注通知。

  用户关注单独保存到 `user_follows`，不与 `topic_follows` 混用。`followed_user_id`
  表示被关注者，`follower_id` 表示关注者；用户改名不影响关系，物理删除账号时级联清理。
  升级先执行 `bin/tasks db.migrate`，再重启服务；不需要回填历史关注。

  登录后，社区列表标题旁提供“全部／仅关注”切换，左侧导航只负责选择节点。
  “仅关注”的地址是 `/forum?following=true`，可与节点组合，例如
  `/forum?node=help&following=true`。切换节点和翻页时保留关注筛选，切换筛选时保留
  当前节点并回到第一页。列表按最后活跃时间排序，每页二十条，翻页只刷新列表。
  从“仅关注”列表进入主题后，详情页也携带 `following=true`，通过侧栏或节点名称返回
  列表时保留筛选。这个参数只表示浏览筛选，不决定用户是否关注当前主题。
  只显示当前用户主动关注且未删除的主题；作者自动接收回复通知，不等于主动关注。

  首次使用通知列表默认显示“全部”，可以切换为“仅未读”；选择保存在当前浏览器 session
  的 `notifications_unread` 中，关闭弹窗后再次打开和翻页均沿用。URL 显式传入
  `only_show_unread=true` 或 `false` 时覆盖保存的选择，不传时沿用 session。仅未读模式下点击
  “全部标为已读”后，保留筛选并显示“没有未读通知”，仍可切回全部查看历史通知。

  在 Markdown 编辑器中输入 @ 后至少两个字符，会在停止输入约 250 毫秒后查询自动补全，
  每次最多返回八个用户。只搜索 login_name，大小写不敏感；候选同时显示昵称和登录用户名。
  每次发布或编辑最多通知五个被提及用户。编辑时可以通知新提及的用户，但同一内容已经
  发送过的同类型通知不会重复发送。

  回复（包括主题关注）和提及通知按收件人、目标 ID、通知类型去重。因此，一个人之前收到
  回复通知，后来又被明确提及，仍然可以收到提及通知。

  允许明确 @自己，但普通的自我回复不会通知自己。

  用户可以在“编辑个人资料”中关闭“接收 @提及通知”。关闭后，不再接收任何人的提及通
  知，包括管理员和自己，同时不再出现在普通用户的 @ 自动补全结果中；管理员补全仍可
  查到该用户，但不会绕过接收设置强制发送提及通知。正常回复通知、管理操作通
  知及历史通知不受影响。重新开启后恢复显示；当前用户开启此设置时，也可以搜索到自
  己。

  正文只为前五个不同的合法登录用户名生成提及链接，大小写不同的同一用户名只占一个
  名额，重复提及不额外占名额，超限部分保留为普通文字。通知使用实际生成链接的用户名
  名单，再筛选存在且允许接收提及通知的用户；链接本身不要求该用户一定存在。

  @ 前可以紧接中文或下划线，例如 hello_@zw963 可以补全并生成提及；紧接 ASCII 字母、
  数字或另一个 @ 时不识别。`\@zw963` 是普通文字，不补全、不生成链接，也不发送提及
  通知。连续反斜杠为偶数时表示普通反斜杠，此后的 @ 仍可被识别。

  代码、已有链接、图片说明、HTML 属性、手写 HTML 的链接和代码等容器，以及 info
  提示框中的 @ 不生成用户链接或提及通知。用户改名后，旧正文中的提及及链接不会改写。

  铃铛显示未读数量，超过九十九条显示 99+。页面加载时更新状态，停留在页面期间通过
  在线人数心跳每两分钟更新一次，不保证别人刚回复后立即显示。打开通知列表或全部标为
  已读后，也会同步更新铃铛。

  打开通知列表不会自动标为已读。点击通知会标记该条已读；打开主题时，还会同步该主题
  及当前阅读位置以内的评论通知，并刷新铃铛计数，不影响之后新增回复的通知。
  “全部标为已读”只清理通知，不修改主题阅读位置；没有未读通知时，该按钮不可用。

  主题阅读同步没有七天限制；七天只用于社区的“近七天未读”筛选。直接打开十天前的主题，
  或从通知跳转到它，仍会标记主题已读并同步相关通知。文档评论不使用主题阅读记录，
  直接打开文档不会批量清理其评论通知。完整规则见[主题未读](topic_unread.md)。

  通知分页读取 `users.notifications_count` 和 `users.unread_notifications_count`，不再
  每次查询通知总数。铃铛和“全部标为已读”按钮也使用未读计数。数据库 trigger 在新增、
  标记已读／未读及删除通知时维护这两个字段，批量已读同样生效，不修改用户编辑时间。
  总数和未读数共用 `add_counters_for`；未读数指定 `soft_delete_column: "read_at"`。
  回填和修复共用 `rebuild_counter_for`，使用相同的外键、软删除字段及筛选条件。
  通知创建后收件人固定，不通过修改 `user_id` 转交通知。

  通知计数和 trigger 已合并进初始建表 migration，空库计数从零开始，无需额外回填。
  如果以后手工修改数据导致计数不一致，可停服后运行 `bin/tasks db.fix.notification_counts`
  重建，避免与新通知并发写入。重建不发通知、不修改通知的已读状态或用户编辑时间。

  点击评论通知后，会加载评论所在的正确分页，必要时展开子评论，再滚动并高亮目标评
  论。该流程通过 comment_id 参数和 Hyperscript 实现，不依赖 URL 锚点。

  管理员编辑主题或评论、移动主题到其他节点，或者删除内容时，作者会收到通知。一次操
  作中修改主题标题或正文算作一条编辑通知；移动主题会记录目标节点名称。这些管理事件
  在不同操作之间不去重。自己编辑、移动或删除自己的内容不会通知自己。

  ### 数据与历史记录

  每条通知保存来源标题，以及原始 Markdown 前 120 个字符的快照，作为普通文本显示。
  移动主题的通知使用目标节点名称作为摘要。

  显示通知时不加载来源记录。后续编辑、软删除不会改变已有快照；编辑中新增加的提及通
  知，保存编辑后版本的快照。

  actor_id 保存实际操作者，例如编辑或删除内容的管理员，而不是内容作者。操作者通过
  关联预加载，因此用户改名后，通知显示其当前名字。

  每条通知保存 `topic_id` 和 `comment_id`，不保存 URL。主题通知只有 `topic_id`，
  主题评论通知两者都有，文档评论通知只有 `comment_id`。评论所属主题另存一份，供按主题
  批量查询通知使用，避免反查评论。两个 ID 至少一个非空，不设目标级联外键。

  `notification.url` 按 ID 动态生成站内地址：有 `comment_id` 时使用 `/comments/:id`，
  否则使用 `/forum/:id`。打开评论地址时会定位评论当前所在的分页，不需要显示列表时加载目标。

  目标已删除或不可访问时，显示友好的 404 页面，并提供进入社区和文档的链接。即使目标
  被物理删除，历史快照仍然保留。

  创建回复和提及通知前，Crystal 代码会检查是否已有同类通知。按主题 ID 查询时，
  `for_target(topic)` 排除评论通知；按评论 ID 查询时，`for_target(comment)` 只匹配该评论。
  索引 `(user_id, topic_id, comment_id, kind)` 支持主题目标查询，也为当前主题已读同步
  提供前缀；另有针对评论通知的 `(user_id, comment_id, kind)` 部分索引。管理操作通知不去重。

  通知目标字段、约束和索引已合并进初始建表 migration，空库直接执行 `bin/tasks db.migrate`，
  无须 URL 回填 task。已部署的目标结构不需要重新迁移；仍保存 URL 的旧库须先使用
  `9865c9e` 版本完成迁移，再更新到压缩后的版本。主题阅读同步复用已有目标字段，无须再改通知表。
