# 主题草稿：按操作流程理解实现

本文只介绍 Topic，不混入评论流程。按打开页面、输入、提交的顺序说明，每一步只讲一个功能。代码行号以本文编写时为准。

## 第一步：打开主题页面，确定草稿归属

先只讲草稿身份，不讲保存和提交。

### 新建主题

改动位置：[new_page.cr 第 18 行](../src/pages/forum/new_page.cr#L18)。

```crystal
data_draft_key: "#{current_user.not_nil!.id}:topic:new"
```

假设当前用户 ID 是 `7`，生成的 HTML 就是：

```html
<form data-draft-key="7:topic:new">
  <!-- 节点、标题、正文 -->
</form>
```

这个标识表示：**用户 7 正在新建的主题草稿**。

用户离开后重新进入发布页，得到的标识仍然相同，JS 就知道应该恢复哪份草稿。换成用户 8，标识是 `8:topic:new`，不会恢复用户 7 的内容。

### 编辑主题

同一个功能，在编辑页的位置是：[edit_page.cr 第 20 行](../src/pages/forum/edit_page.cr#L20)。

```crystal
data_draft_key: "#{current_user.not_nil!.id}:topic:#{topic.id}:edit"
```

用户 7 编辑主题 42 时，标识就是：

```text
7:topic:42:edit
```

这样，新建主题、编辑主题 42、编辑主题 43，各自有独立的草稿。

**这一步只是给表单标记身份，不读取数据库，也不保存草稿。**JS 后面会拿这个标识作为本地存储的 key。

## 第二步：标记哪些字段需要保存

主题草稿要保存三个字段：**节点、标题、正文**。因此，给它们分别增加 `data-draft-field` 标记。

1. 节点选择框：[topic_fields.cr 第 20 行](../src/components/forum/topic_fields.cr#L20)。
2. 标题输入框：[topic_fields.cr 第 37 行](../src/components/forum/topic_fields.cr#L37)。
3. 正文输入框：[editor.cr 第 106 行](../src/components/comments/editor.cr#L106)。

三个位置增加的内容都一样：

```crystal
data_draft_field: ""
```

Crystal 会把它输出成 HTML 属性 `data-draft-field=""`。这里的空字符串**不代表清空输入内容**，只是标记“这个字段需要保存”。

结合上一步，最终结构类似：

```html
<form data-draft-key="7:topic:new">
  <select name="topic:node_id" data-draft-field=""></select>

  <input name="topic:title" data-draft-field="">

  <textarea name="content" data-draft-field=""></textarea>
</form>
```

JS 看到这个结构，就知道：

```text
草稿身份：7:topic:new

需要保存：
  topic:node_id -> 选中的节点
  topic:title   -> 输入的标题
  content       -> 输入的正文
```

正文虽然写在名叫 `Comments::Editor` 的组件里，但主题页面也复用这个编辑器，调用位置在 [topic_fields.cr 第 49 行](../src/components/forum/topic_fields.cr#L49)。

**到这里仍然只是标记，没有执行保存。**

## 第三步：页面打开后，恢复已有草稿

这一步没有新增 Crystal 逻辑，前面生成的 HTML 标记交给 JS 使用。

入口在 [app.js 第 65 行](../src/js/app.js#L65)：

```javascript
findElements(root, "[data-draft-key]").forEach(setupDraft);
```

意思是：找到带草稿标识的区域，调用 `setupDraft` 初始化。

具体恢复逻辑在 [drafts.js 第 4 行](../src/js/drafts.js#L4)。继续使用前面的例子：

```html
<form data-draft-key="7:topic:new">
```

JS 给这个标识加上固定前缀，得到本地存储的 key：

```text
draft:7:topic:new
```

假设浏览器里已经保存了：

```json
{
  "topic:node_id": "3",
  "topic:title": "还没写完的主题",
  "content": "这是尚未提交的正文"
}
```

JS 就根据各字段的 `name`，把值分别填回节点选择框、标题输入框和正文输入框。

**如果没有对应草稿，就保持服务器生成的原始内容不变**：新建页通常为空，编辑页则是已保存的主题内容。

这个过程只读取浏览器本地存储，不发送请求，也不会修改数据库。

## 第四步：用户输入时，保存草稿

这一步也没有 Crystal 改动，由 [drafts.js 第 22 行](../src/js/drafts.js#L22) 监听：

```javascript
container.addEventListener("input", save);
container.addEventListener("change", save);
```

意思是：在这个主题表单里输入文字、改变选择等操作发生时，调用 `save`。

保存逻辑在 [drafts.js 第 25 行](../src/js/drafts.js#L25)：读取前面标记过的三个字段，将它们**一起写入同一份草稿**。

例如你输入：

```text
节点：求助，ID 为 3
标题：Channel 怎么关闭？
正文：我遇到了一个问题……
```

浏览器本地存储就变成：

```text
key：draft:7:topic:new
```

```json
{
  "topic:node_id": "3",
  "topic:title": "Channel 怎么关闭？",
  "content": "我遇到了一个问题……"
}
```

继续输入时，会覆盖更新这份草稿，不会不断新增记录。

**主动清空字段，也会保存空字符串。**否则你把标题删掉后刷新，可能又恢复出之前的旧标题。

保存发生在输入变化时，不需要等待离开页面，也不发送服务器请求。因此刷新、关闭浏览器或离开发布页，都不依赖“退出时保存”。

## 第五步：发布失败时，保留草稿

这里分两种情况。

### 网络失败

请求没有成功完成，浏览器里的草稿不做任何清理。你输入时已经保存了内容，所以刷新后可以恢复。

这不需要额外的 Crystal 处理。

### 服务端校验失败

位置：[create.cr 第 12 行](../src/actions/forum/create.cr#L12)。

```crystal
else
  build_failed_flash(operation)

  html Forum::NewPage, operation: operation
end
```

这段逻辑原来就有：保存失败，重新显示发布表单和错误提示。

**这次新增的是保持编辑页地址不变。**

位置：[new_page.cr 第 17 行](../src/pages/forum/new_page.cr#L17)。

```crystal
hx_push_url: "false",
```

例如：

```text
打开发布页：      /forum/new
提交到：          POST /forum
校验失败后地址：  仍然是 /forum/new
```

这样按 F5，仍然打开发布页，而不是进入 `/forum` 主题列表。发布页重新生成相同的草稿 key，JS 就能恢复内容。

编辑主题同理，[edit_page.cr 第 18 行](../src/pages/forum/edit_page.cr#L18) 也加了这个设置。

另外，**JS 不会仅凭 HTTP 200 就清除草稿**，因为上面的校验失败页面也可能返回 200。它只认服务器明确返回的“保存成功”标记；失败响应没有这个标记，就继续保留。

## 第六步：保存成功后，返回明确的成功标记

先看调用位置：

- 新建主题：[create.cr 第 11 行](../src/actions/forum/create.cr#L11)。
- 编辑主题：[update.cr 第 18 行](../src/actions/forum/update.cr#L18)。

原来保存成功后直接 `redirect`，现在统一调用：

```crystal
redirect_after_save(topic)
```

**数据库保存逻辑没有改变**，改的是保存成功后如何响应浏览器。

具体实现在 [forum_action.cr 第 8 行](../src/actions/forum_action.cr#L8)。

对于 HTMX 请求，关键代码是：

```crystal
flash.keep
context.response.headers["X-Draft-Saved"] = "true"
context.response.headers["HX-Location"] = path

head 200
```

这几行分别负责：

- `flash.keep`：保留成功提示，让接下来的主题详情页显示。
- `X-Draft-Saved`：本站自定义响应头，告诉草稿 JS，数据库确实保存成功，可以清除草稿。
- `HX-Location`：HTMX 支持的响应头，告诉它接下来进入哪个页面。
- `head 200`：返回这些响应头，不返回页面 HTML。

假设新主题 ID 是 `42`，浏览器收到：

```http
HTTP/1.1 200 OK
X-Draft-Saved: true
HX-Location: /forum/42
```

### 为什么不继续使用原来的 HTTP 重定向？

因为浏览器会自动跟随重定向，JS 最后拿到的是详情页响应，读不到中间响应里的 `X-Draft-Saved`。

现在让浏览器先收到成功标记，再由 HTMX 进入详情页，就能先清理草稿。

普通非 HTMX 请求不需要这套处理，[forum_action.cr 第 19 行](../src/actions/forum_action.cr#L19) 仍然使用原来的 `redirect`。

## 第七步：清除本次提交对应的草稿

入口在 [app.js 第 31 行](../src/js/app.js#L31)：

```javascript
document.addEventListener("htmx:after:request", clearSavedDraft);
```

请求完成后，调用 [drafts.js 第 36 行](../src/js/drafts.js#L36) 的 `clearSavedDraft`。

它先检查两个条件：

```text
响应是否成功？
是否带有 X-Draft-Saved: true？
```

都满足，才清理草稿。

继续之前的例子，你提交的表单是：

```html
<form data-draft-key="7:topic:new">
```

JS 从发起请求的元素向外找到这个表单，读取标识，删除本地存储中的：

```text
draft:7:topic:new
```

**只删除这一份，不会清空其他主题的编辑草稿。**

注意：即使发表后新主题的 ID 是 `42`，清理的仍然是 `7:topic:new`，不是 `7:topic:42:edit`。因为清理依据是**本次提交的表单标识**，不是新主题的 ID。

清理完成后，HTMX 再根据上一阶段收到的：

```http
HX-Location: /forum/42
```

进入主题详情页。以后重新进入发布页，因为原草稿已经删除，就不会再次恢复刚刚发表的内容。

到这里，主题草稿的完整流程就结束了。
